# MVP0 — Fundação web

**Estado:** desenho aprovado pelo PI
**Data:** 2026-09-13
**Tipo:** fundação comprovada por fluxo vertical
**Fora de escopo:** `docs/FORA-DE-ESCOPO.md`, seção "MVP0 — Fundação web"

## 1. Objetivo

Entregar uma aplicação web local utilizável em que um proprietário cria e confirma sua conta, entra com sessão segura, cria uma organização, cadastra fazendas e cadastra talhões por desenho no mapa ou importação GeoJSON. O fluxo deve provar API, banco geoespacial, fila, e-mail, auditoria, isolamento de tenant, interface web e CI trabalhando em conjunto.

O MVP0 não é considerado concluído se entregar apenas scaffolding ou serviços vazios.

## 2. Usuário e resultado observável

**Usuário:** proprietário rural responsável por uma ou mais fazendas.

Ao final, uma instalação limpa deve permitir:

1. criar usuário com e-mail e senha;
2. receber e usar confirmação de e-mail no Mailpit local;
3. autenticar, encerrar sessão e recuperar senha;
4. criar uma organização;
5. cadastrar várias fazendas por nome, estado e município;
6. cadastrar talhão desenhando polígono ou importando GeoJSON;
7. visualizar fazendas e talhões em lista e mapa;
8. impedir que outro tenant leia, altere ou infira esses objetos;
9. rastrear ações administrativas por correlação e auditoria.

## 3. Escopo

### Dentro

- monorepo com backend Python/FastAPI e web React/TypeScript;
- PostgreSQL 16 com PostGIS; Redis; Celery; Mailpit;
- ambiente local isolado por Docker Compose;
- autenticação por e-mail/senha, confirmação, sessão revogável e recuperação;
- organização como tenant; um usuário pode possuir organizações por vínculo explícito;
- papel único `owner`; sem convites no MVP0;
- CRUD web de organização, fazenda e talhão;
- fazenda identificada por nome, UF (sigla) e município (código IBGE + nome, via seed), sem CPF/CNPJ;
- desenho no mapa e importação GeoJSON;
- cálculo de área no backend a partir da geometria canônica;
- auditoria mínima, correlação, tratamento padronizado de erros e CI.

### Fora

O recorte detalhado e seus gatilhos ficam exclusivamente em `docs/FORA-DE-ESCOPO.md`. Em resumo: mobile/offline, KML, cloud, microserviços, produto financeiro/fiscal, WhatsApp/IA e compliance não entram no MVP0.

## 4. Arquitetura

```text
React Web
   ↓ JSON + cookie de sessão
FastAPI — monólito modular
   ├─ identity
   ├─ organizations
   ├─ farms
   ├─ fields
   └─ audit
        ↓
PostgreSQL/PostGIS
        ↓ outbox
Celery + Redis ─> confirmação e recuperação de senha ─> Mailpit
```

- FastAPI organiza contratos por `APIRouter`; dependências resolvem sessão, tenant ativo e autorização.
- O domínio não depende do framework HTTP nem do ORM.
- Celery é provado por envio real de confirmação/recuperação; tarefa recebe IDs, é idempotente e usa retry limitado com backoff.
- E-mail criado com sucesso não é revertido por falha temporária de entrega; o job permanece recuperável.
- Nenhum serviço é separado por deploy no MVP0 (ADR-002 — monólito modular).

## 5. Modelo de dados mínimo

| Entidade | Dados essenciais | Invariantes |
|---|---|---|
| `User` | id, e-mail normalizado, hash, estado, timestamps | e-mail único normalizado; senha nunca persistida em claro |
| `Organization` | id, nome, timestamps | raiz do tenant |
| `Membership` | user, organization, role | par único; apenas `owner` no MVP0 |
| `Session` | hash do token, user, expiração, revogação | token de uso externo não é armazenado em claro |
| `EmailVerificationToken` | hash, user, expiração, uso | uso único |
| `PasswordResetToken` | hash, user, expiração, uso | uso único; resposta não enumera e-mail |
| `Farm` | id, tenant, nome, UF (sigla), município (código IBGE) | não possui CPF/CNPJ no MVP0 |
| `Field` | id, tenant, farm, nome, geom, area_ha | pertence à fazenda/tenant; área calculada no servidor |
| `Municipio` (seed) | código IBGE (7 dígitos), nome, UF | referência para validação de `Farm`; carregado por seed, não hardcoded |
| `OutboxEvent` | id, tipo, payload mínimo, estado | criado na mesma transação do fato |
| `AuditEvent` | ator, tenant, ação, objeto, correlação, resultado, instante | append-only; sem senha/token |

Geometria canônica: `geometry(MultiPolygon, 4674)`. GeoJSON `Polygon` válido é normalizado para `MultiPolygon`; a API rejeita outros tipos, geometria inválida ou fora do bounding box do Brasil (SPEC-005). A área é calculada de forma geodésica no backend e persistida com 4 casas decimais (SPEC-005).

## 6. Autenticação e autorização

- Sessão em cookie `HttpOnly`, `SameSite` apropriado e `Secure` fora do HTTP local.
- Proteção CSRF em operações mutáveis; rotação após autenticação e revogação no logout/reset.
- Hash de senha moderno com parâmetros versionados e possibilidade de rehash.
- Confirma/recuperar não revela se um e-mail existe.
- Tenant ativo vem de vínculo autorizado, nunca de header confiado isoladamente.
- Toda leitura/mutação verifica organização e objeto; RLS no PostgreSQL atua como defesa adicional com default deny.
- MFA de dono/contador fica fora do MVP0 (`docs/FORA-DE-ESCOPO.md`); entra no MVP-001 quando a SPEC de identidade correspondente for aberta.

## 7. Fluxos

### Cadastro e confirmação

Web envia cadastro → API cria usuário pendente e evento de outbox na mesma transação → Celery envia link ao Mailpit → link de uso único confirma → usuário pode autenticar. A confirmação não cria sessão automaticamente; o usuário retorna ao login.

### Recuperação

Solicitação sempre responde de forma neutra → token hash de uso único e outbox → Celery/Mailpit → nova senha revoga sessões e tokens anteriores.

### Fazenda e talhão

Usuário escolhe organização autorizada → cadastra fazenda → desenha ou importa GeoJSON → navegador mostra prévia → API valida, normaliza, calcula área e persiste → mapa consulta somente dados do tenant ativo.

## 8. Erros e estados de interface

- API usa `application/problem+json` com `type`, `title`, `status`, `code` e `correlationId`.
- Tentativa entre tenants não revela existência do objeto.
- Geometria inválida informa erro acionável sem aceitar área calculada no cliente.
- Conflito de nome não sobrescreve registro; unicidade de nome não será presumida sem SPEC.
- React representa explicitamente `idle`, `loading`, `submitting`, `success`, `empty` e `error`.
- Formulário não manipula DOM diretamente e preserva dados quando erro recuperável ocorrer.

## 10. Comandos públicos exigidos

A implementação deve fornecer comandos equivalentes, executáveis no Windows, sem exigir que o PI conheça comandos internos de Python ou Node:

```powershell
npm run dev
npm run stop
npm run build
npm run lint
npm run typecheck
npm test
npm run test:e2e
```

`npm run dev` sobe dependências e aplicações; `npm run stop` encerra somente containers do SafraOS. A CI chama os mesmos contratos ou wrappers equivalentes, sem lógica essencial exclusiva de shell Linux.

## 11. Estratégia de testes

| Nível | Provas mínimas |
|---|---|
| unidade | senha/token, expiração, normalização, regras de vínculo e GeoJSON |
| banco | migrations, constraints, PostGIS, área, transação, RLS e isolamento |
| integração | FastAPI + PostgreSQL + Redis + Celery + Mailpit reais em Docker |
| web | formulário/mapa e estados de loading, vazio, erro e sucesso |
| segurança | CSRF, sessão, enumeração, autorização por objeto e dois tenants |
| E2E | cadastro → confirmação → login → organização → fazenda → talhão |
| assíncrono | retry, reentrega idempotente e falha temporária de e-mail |
| performance | mapa com massa de 500 talhões numa fazenda (SPEC-005) |

Não há percentual de cobertura como substituto. Os riscos acima precisam de prova rastreável ao SHA.

## 12. Limites de decisão

### Sempre fazer

Validar entrada no backend; testar isolamento; usar migration; preservar correlação; executar lint/typecheck/testes; documentar limitação real.

### Perguntar antes

Adicionar dado fiscal à fazenda; introduzir novos papéis/convites; mudar cookie por JWT no navegador; alterar forma de tenant; adicionar cloud; incluir item de `FORA-DE-ESCOPO.md`.

### Nunca fazer

Confiar `tenant_id` enviado pelo cliente; guardar senha/token em claro; armazenar sessão no `localStorage`; aceitar área calculada pelo navegador como canônica; remover RLS/teste para acelerar CI; iniciar mobile neste MVP.

## 13. Critérios de aceite do MVP0

- instalação limpa sobe localmente pelos comandos documentados;
- fluxo completo passa em navegador real e em CI;
- dois tenants não leem, alteram nem inferem objetos um do outro;
- área persistida é calculada no backend a partir de geometria válida, com 4 casas decimais;
- confirmação e recuperação usam Celery/Redis/Mailpit, com retry/idempotência provados;
- logs permitem correlacionar requisição, transação/outbox e job sem expor segredo;
- build, lint, typecheck, banco, web, segurança e E2E passam no SHA atual;
- documentação operacional e evidências estão atualizadas;
- nenhum item registrado como fora de escopo foi implementado por conveniência.

## 14. Decomposição prevista

O MVP0 está dividido em fatias verticais, cada uma com SPEC/F próprios:

1. `SPEC-001/F1` — fundação executável e CI;
2. `SPEC-002/F2` — identidade, sessão e e-mail assíncrono;
3. `SPEC-003/F3` — organização, tenancy e auditoria;
4. `SPEC-004/F4` — fazendas;
5. `SPEC-005/F5` — talhões, GeoJSON e mapa;
6. gate de homologação do MVP0, sem SPEC/F.
